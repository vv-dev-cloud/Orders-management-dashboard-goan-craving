# Goan Craving ecosystem integration contract

**Status: Phase 0 contract, not yet an implemented cross-service integration.** This document records the current source-of-truth findings and the target contract. Do not assume an API, event, collection, or field described as target is already deployed.

## Canonical identifiers and data ownership

- The customer website owns order creation and the MongoDB `foodorders` collection (`FoodOrder`). The immutable MongoDB order `_id` is the canonical `orderId`; the human-readable `orderNumber` (currently `GC-` plus the final eight ID characters) is for display/search only.
- The customer website owns the `deliverytasks` collection (`DeliveryTask`) as the intended assignment record. Its current schema has one unique task per order, a `deliveryPerson` reference, pickup/dropoff coordinates, a status, and event history. Reassignment history and a separate public `assignmentId` are not yet fully modelled.
- Delivery-agent credentials are stored in the shared `users` collection. The Order Management `DeliveryAgent` model and Delivery Dashboard `User` model both target this collection. Never create a second agent identity for the same person.
- The Order Management dashboard reads `foodorders` through a `FoodOrder` model. The current Delivery Dashboard `Order` model instead uses its own default `orders` collection and a different order shape. This is a known integration mismatch; do not silently treat these records as synchronized.
- Admin reporting must read authorized, authoritative data from the owning service/database. It must not infer or fabricate platform-wide totals from its local employee collection.

## Status ownership

- Customer/order status is owned by the customer order record and employee-approved operations workflow.
- Delivery-agent actions are reports, not final order decisions. Agent-reported outcomes must not directly mark an order as delivered.
- The DeliveryTask lifecycle is assignment/fulfilment state. The FoodOrder lifecycle is customer-facing order state. Keep them separate.
- An employee in Order Management verifies a delivery report and then authorizes the final customer-visible order transition.
- Preserve legacy values already present in production; use backward-compatible transitions and explicit mapping rather than destructive renames.

## Target delivery task fields

The target contract should retain the existing `DeliveryTask` fields and evolve compatibly to include:
- `order`: canonical FoodOrder ObjectId (unique active task per order unless a later version explicitly supports multiple attempts).
- `deliveryPerson`: shared `users` ObjectId.
- `status`: `pending_assignment | assigned | accepted | at_restaurant | picked_up | en_route | delivered | assignment_failed | delivery_failed | cancelled | returned`.
- `events[]`: append-only actor, role, status, timestamp, and reason/note.
- A stable public `assignmentId` and version/idempotency token before supporting reassignment or retry workflows.
- Agent location only when the agent has explicitly enabled location sharing and is on duty; include `lastUpdatedAt` and treat stale coordinates as unavailable.

## Required service boundaries

1. Customer website: validates customer ownership, persists order/address snapshot, and exposes only customer-safe tracking fields.
2. Order Management: reads canonical orders, creates/assigns delivery tasks, handles employee verification, and owns final operational decisions.
3. Delivery Dashboard: authenticates the existing shared agent account; reads only tasks assigned to the signed-in agent; submits agent reports and permitted location updates.
4. Admin Dashboard: authorized read-only cross-service reporting first; privileged mutations require role checks and audit records.

## ETA contract

ETA must be calculated server-side from validated coordinates and route-provider results (Stadia Maps, where configured), not generated by an LLM. The calculation should include restaurant preparation time, available-agent-to-restaurant travel, restaurant-to-customer route time, and a handover/operational buffer. Recalculate when assignment, route, agent availability, or preparation state changes. If coordinates/provider results are missing or stale, show an honest unavailable/approximate state rather than inventing a precise ETA. Keep `OPENROUTER_API_KEY` server-side and never use an LLM as a routing engine.

## API/event requirements before production wiring

- Use authenticated service-to-service requests; never expose shared service credentials in browser JavaScript.
- Every mutation must validate actor role and record ownership.
- Use the canonical `orderId`, stable `assignmentId`, and idempotency key for retry-safe writes.
- Events should include `eventId`, `eventType`, `orderId`, optional `assignmentId`, `occurredAt`, `actor`, and a schema version.
- Persist the database change before publishing an event; consumers must deduplicate and tolerate out-of-order/retried delivery.
- Do not trust a browser-supplied price, total, payment state, employee identity, or final delivery status.

## Rollout and acceptance gates

- First reconcile the Delivery Dashboard's current `orders` collection with canonical `foodorders` and `deliverytasks`; do not switch live reads until compatibility and existing records are understood.
- Add contract tests for shared order IDs, agent identity, assignment ownership, duplicate submissions, employee verification, and customer-safe status mapping.
- Verify all four repositories against the same staging database and non-production service credentials before production rollout.
- Never merge or deploy automatically; review the feature branch, test evidence, and migration/rollback plan first.

## This repository's responsibility
Order Management: own employee decisions, assignment orchestration, delivery-agent provisioning, ETA coordination, and support handoff.
